# 运输交接对账 v1

为运营对账者把两条独立来源的发运与签收记录，按指定版本仓库中的链路端点，
逐链路按时间合并成可独立读取的 SQLite 对账库。它回答“哪些发运被哪些签收按
先发先出消耗、哪些签收量无处可抵、哪些发运余额仍未签收、每个节点收发多少”，
**不是**路径规划、库存估值、计费结算或物理运输仿真。

## 输入

两个 CSV 文件，表头必须恰好为 `id,link_id,time,quantity`（UTF-8，允许 BOM；
列顺序固定，不允许多余列或空行）：

| 列 | 含义 |
| --- | --- |
| `id` | 该行在本文件内唯一的标识，1..128 字符，首尾无空白、无控制字符 |
| `link_id` | 必须出现在所选 revision 的快照链路中；端点即取自该快照 |
| `time` | ISO-8601 且**必须带显式时区**（`Z`、`+hh:mm`、`-hh:mm`），统一换算为 UTC |
| `quantity` | 1..10^9 的十进制整数（不含符号、小数点、前导空白） |

时间接受可选的 1..9 位小数秒；输出统一为 `YYYY-MM-DDThh:mm:ss[.fraction]Z`，
小数部分去除尾随零。缺少时区、非法日历值、超出 UTC 年份范围的输入一律拒绝，
不做“本地时间”猜测。

输入行顺序任意，文件内与文件间都不要求排序。

### 去重与冲突

* 发运表与签收表**各自**按 `id` 去重；内容相同（`link_id`、UTC 时刻、数量都
  一致）的重复行只计一次，并在 `reconciliation` 中如实统计行数、唯一数与
  重复数。
* 同一个 `id` 出现内容不同的行即报错，消息给出**文件路径、冲突行号**以及首次
  出现的行号；不发运、不签收、不发布任何结果。
* 发运与签收的 `id` 属于两个独立命名空间，可以相同。

## 匹配规则

每条链路独立处理，事件按 `(UTC 时刻, id)` 排序；**同一时刻发运先于签收**。

1. 签收按时间顺序逐条处理，从该链路最早尚未耗尽的发运开始按 FIFO 消耗，
   允许拆分：一条签收可跨多条发运，一条发运也可被多条签收部分消耗。
2. 签收只能消耗**时刻不晚于它**的发运。既然事件已按时间排序，当前时刻之后
   才出现的发运永远不可能被此前签收借用。
3. 无处可抵的签收量记为孤儿：该链路首笔可达发运之前的记 `early_arrival`，
   有发运但余额已尽的记 `over_receipt`。整条签收部分匹配、部分孤儿是允许的。
4. 全部签收处理完后仍有余额的发运记为未签余额（`unmatched_shipments`），
   数量为该发运的剩余量。

同一输入（无论数组/行顺序如何）结果确定：匹配明细的主键是
`(link_id, receipt_id, shipment_id)`，FIFO 顺序由时间与 id 唯一确定。

## 输出

输出是**一个独立 SQLite 文件**（非仓库副本，读取方无需仓库或其他程序）：

| 表 | 内容 |
| --- | --- |
| `reconciliation` | 单行台账：`schema_version`、`revision`、`snapshot_id`、两源文件 SHA256、行数/唯一数/重复数、各总量与链路/节点计数 |
| `matches` | 匹配明细：链路、签收 id 与 UTC 时刻、发运 id 与 UTC 时刻、消耗数量 |
| `unmatched_shipments` | 未签余额：链路、发运 id、UTC 时刻、剩余数量 |
| `orphan_receipts` | 孤儿签收：链路、签收 id、UTC 时刻、数量、原因（`early_arrival`/`over_receipt`） |
| `links` | 每链路收发与匹配/孤儿/未签汇总，含该版端点 `from_node`/`to_node` |
| `node_summary` | 每节点：发出量、收到量、其中已匹配签收量、孤儿签收量、未签发运量 |

`node_summary` 按端点归属：发运数量计入 `link.from_node` 的发出量，签收数量计入
`link.to_node` 的收到量，孤儿量与未签余额分别计入对应节点的列。节点集合取自
所选 revision 的全部节点，没有流量的节点也保留为零行。

对账库以 `PRAGMA integrity_check` 可独立校验，且落盘后再次用 SQL 汇总核验
守恒：`匹配 + 孤儿 = 签收总量`、`匹配 + 未签 = 发运总量`。绑定字段
`snapshot_id` 在读入时对快照内容重算 SHA256 并与版本仓库记录比对，防止读到
被替换的快照。

## 资源与发布

* 200 万行输入（每表 100 万）实测新增峰值内存 ≤ 64 MiB；全部中间态在临时磁盘
  完成，临时目录随操作结束删除。内存测量用真实 CLI 子进程的 `ru_maxrss`。
* 不逐单位匹配：数量为 10^9 的发运与签收仍只产生一行匹配。不重扫全部发运：
  每条链路使用两个只向前推进的磁盘游标，签收按发运**段**推进。
* 匹配明细直接流式写入输出库，不积存在内存。
* 输出先在目标目录内的临时文件构建，全部校验通过后 `fsync` 并原子替换；
  解析、链路解析或发布失败时保留旧结果，不留下半成品或临时文件。
* 源仓库以只读 URI 打开（无活跃 WAL 时用 `immutable=1`），绝不写入源仓库，
  也不在其旁边创建 WAL 边车文件。

## 退出码

`0` 成功；`2` 输入/校验/IO/发布错误。成功时向标准输出打印一行 JSON 摘要
（与 `reconciliation` 行内容一致，另含 `output` 路径）。
